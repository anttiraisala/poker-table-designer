# CLAUDE.md

Working rules and design decisions for AI assistants (and humans) working on **Poker Table Designer**.

## Project in one paragraph

A browser-based, CAD-like design tool for poker tables, built for the Molino Royale home casino. Phase focus: the printed or vinyl pattern for the table cloth (logo, text, lines, cards) in real millimetres, checked against one or more table outlines, with cut export for a vinyl cutter. Later: the table structure (board, foam, rail). See [PROGRESS.md](PROGRESS.md) for status and [README.md](README.md) for usage.

## Repository conventions

- Branch: `master`. Licence: MIT. No build step, no dependencies for the core page.
- `index.html` is the source of truth: a complete standalone page that opens directly in a browser and is served by GitHub Pages (Settings, Pages, Deploy from a branch, `master`, `/ (root)`). Live URL: https://anttiraisala.github.io/poker-table-designer/
- The same code must also run as a Claude Artifact. The Artifact host wraps the file itself, so run `python3 scripts/make-artifact.py` to produce `dist/artifact.html` (no doctype, html, head or body tags) and publish that file. Never hand-edit the generated file.
- Artifact limits to respect: scripts only from approved CDNs (cdnjs, jsdelivr, unpkg), stylesheets only from Google Fonts, no network calls to other hosts, no `window.print()`, files leave the page as downloads. Code that depends on these must degrade gracefully when the page runs standalone.
- Code layout: `index.html` (skeleton), `css/app.css`, and classic scripts in `js/` that share the `window.PTD` namespace (no ES modules, so the page also works from `file://`): `geom.js` (arcs, offsets, presets; also runs in Node), `solver.js` (guide constraints; also runs in Node), `fonts.js`, `tables.js`, `guides.js`, `measure.js` (lasting measurements, ghost preview, text tracing), `calfit.js` (calibration maths; also runs in Node), `pdf.js` (tiny PDF writer; also runs in Node), `calibration.js` (calibration images for the cutter), `cutters.js` (cutter list, calibration entry, measuring guide window and PDF), `help.js` (tooltips, help window, examples), `eps.js` (EPS writer for Roland CutStudio; also runs in Node), `sheet.js`, `export.js`, `scene.js` (objects on the table: pot, burn cards, muck, players, dealer button; one generator for the stage, the picture and Blender), `words-basic.js` (GENERATED from `data/words-basic.json` by `python3 scripts/make-words-js.py`; never edit it by hand, edit the JSON and regenerate), `words.js` (word banks: merge, project and universal lists), `random.js` (randomizer and casino-name inventor), `jsonbox.js` (JSON window), `app.js` (core, loaded last). `js/blender-template.js` is generated from `blender/src/scene_template.py` by `scripts/make-blender-js.py`; never edit it by hand. Keep `index.html` loadable without a build step.
- Tests: `node tests/geom.test.js`, `node tests/solver.test.js`, `node tests/eps.test.js`, `node tests/calfit.test.js`, `python3 tests/blender_mock.py script.py --expect-project` (runs a generated Blender script against a stand-in bpy; `tests/e2e.js` calls it), and the Playwright browser tests `tests/e2e.js`, `tests/e2e-more.js`, `tests/e2e-mocks.js`, `tests/e2e-parts.js`, `tests/e2e-extras.js`, `tests/e2e-scene.js`, `tests/e2e-origin.js`, `tests/e2e-convert.js`, `tests/e2e-shapes.js` and `tests/e2e-words.js` and `tests/e2e-measure.js`, `tests/e2e-calibration.js`, `tests/e2e-help.js`, `tests/e2e-names.js` and `tests/e2e-cutters.js` (Playwright is not a project dependency; see the file headers).
- Do not commit third-party font files or other assets without a licence that allows redistribution. Fonts are loaded from Google Fonts or imported by the user from a file. One deliberate exception, decided by the maintainer: `fonts/porcelain/PORCELAIN.TTF` is committed with a `NOTICE.md` that records its origin and that its licence is unverified.
- Version tag: the page shows `V<number> · <YYYYMMDDhhmm>` (UTC+2) under the title. Run `python3 scripts/stamp-version.py` right before every commit (it writes `js/version.js`; never edit that file by hand).
- Verify what you can (syntax checks, small node tests). State plainly in PROGRESS.md what was and was not tested in a real browser.

## Release routine and running the tests

Do these steps in this order for every change that is released (the maintainer expects a commit, a push and a published Artifact each time he asks for a change to be done):

1. Run all tests (below). Fix what fails; do not release red tests.
2. Update the documents that the change touches: this file (design decisions), `README.md` (usage) and `PROGRESS.md` (a milestone row, the testing honesty text, planned work and open questions).
3. If `data/words-basic.json` changed, `python3 scripts/make-words-js.py`. Then `python3 scripts/stamp-version.py` (writes `js/version.js`), then `python3 scripts/make-artifact.py` (writes `dist/artifact.html`).
4. `git add -A`, then `git commit` with an English message. End the message with the attribution lines that the tool environment gives for the session (a `Co-Authored-By:` line and a `Claude-Session:` line).
5. `timeout 100 git push -q origin master`, then check `git status -sb` shows no `ahead`.
6. Publish `dist/artifact.html` to the existing Artifact (same URL, so the link stays). The Artifact is private and its address is not stored in the repository: ask the maintainer for it if you do not have it. Pure documentation changes need no new Artifact.

Running the tests:

- Node tests need nothing: `node tests/geom.test.js`, `node tests/solver.test.js`, `node tests/eps.test.js` and `node tests/calfit.test.js`. `scripts/make-cutstudio-tests.js` writes the CutStudio test files in `tests/cutstudio/`; run it again whenever `js/eps.js` changes (eps.test.js fails when they are stale).
- Browser tests use Playwright with Chromium, which is not a project dependency. Install it globally (`npm install -g playwright`, then `npx playwright install chromium`) and run each file from the repository root with `NODE_PATH=$(npm root -g) node tests/<file>.js`: `e2e.js`, `e2e-more.js`, `e2e-mocks.js`, `e2e-parts.js`, `e2e-extras.js`, `e2e-scene.js`, `e2e-origin.js`, `e2e-convert.js`, `e2e-shapes.js`, `e2e-words.js`, `e2e-measure.js`, `e2e-calibration.js`, `e2e-help.js`, `e2e-names.js`, `e2e-cutters.js`. Each prints `ok` or `FAIL` lines and ends with `all passed` or `N FAILED`. The whole set takes a few minutes; run files one at a time if a tool has a time limit.
- The page is opened from `file://`, so Google Fonts, opentype.js and Paper.js fail to load offline; the tests expect that (the mocked-library tests cover those code paths).
- Known flake: `e2e.js` has occasionally shown one failing check that passed on the next run. Rerun a failing file once before digging; if it fails twice, it is real. The randomizer waits up to 2.5 s for fonts, so tests that depend on it poll or wait at least 3 s.
- Blender: `python3 tests/blender_mock.py <script.py> --expect-project` runs a generated script against a stand-in `bpy`. Real Blender is not available in the development environment.
- New behaviour needs a test in the matching file (or a new `tests/e2e-<topic>.js`, which must also be listed in this file and in the README). Tests that depend on the default layout must start from a neutral state (see the first lines of `tests/e2e.js`).

## Standing rule for every JSON in the program (given by the maintainer, 2026-11-05)

Every kind of JSON data in this program (project and its parts, settings, word lists, and any new kind such as the cutter list) must be importable and exportable through a copy-paste window (the JSON window in `js/jsonbox.js`, with Copy, Paste, Apply, OK and Cancel), in addition to file Save and Open. A new JSON kind is not finished until it has its own JSON window part, an import that finds the kind from the keys, a button for the window in its panel, a tooltip, and a test of the paste round trip. Today's parts are `project`, `artwork`, `tables`, `words`, `universal`, `settings` and `cutters` (a `cutters` list replaces the list; a single cutter object is added, or replaces the one with the same name).

## Design decisions (agreed with the maintainer)

- **Units:** all geometry in millimetres. Old logo-editor settings JSON loads as the artwork part (1 unit = 1 mm).
- **Files:** one settings (config) JSON (units, snapping, the list of cutters with their calibration, the heat press size, favourite fonts, own universal words; see Settings file versus project file below) and one project JSON (tables, guides, constraints, artwork, export choices). Both carry a format name and version. Keys are English with units in names (for example `fontSizeMm`). Open and Save use the file picker and downloads; the browser also autosaves. A project file may be partial: `artwork` (layers, band, cards), `cloth` and used fonts and colours; or `tables`, `guides`, `constraints` and used colours. Save offers Project, Artwork only and Tables only; Open merges everything the file contains and keeps the rest (palette merges by id unless the file has both parts; fonts merge by family; `name` applies unless the file holds exactly one of the two groups; export references to missing tables reset). Old logo-editor settings load as artwork only.
- **Randomizer:** a Random tab shuffles fonts, sizes and layout of the existing texts on a timer (optionally also table shapes) and can invent a casino with helper texts. Words of user texts are never changed unless the "change the words" box is ticked (then every round invents a new casino name and helper texts, replacing all texts, as one undo step), texts stay inside the player area (bet-line inset of the first visible table), partial overlap is allowed, colours are never changed. Every round is its own undo step and nothing is selected afterwards, so a stopped run can be stepped through with Undo and Redo; one Create casino is one step; Undo while it runs stops it first. Invented names and helper texts never repeat a word, and "EST." appears at most once. Ten properties have a row of Vary, Set and value boxes: the player-area line, the dealer notch, the poker hand, the pot, the burn cards, the muck and Show players, and three rows under Show players (number of players 1 to 12, cards per player 2 to 4, dealer is a player). Vary changes it at random in every round (per visible table for the table properties, with a new arrangement whenever a player property varies); Set replaces it with the chosen value and wins over Vary. Show players decides first; the rows under it are only decided on tables that show their players, are disabled when Show players is set hidden, and ticking Vary or Set on one of them switches Show players on (Set) unless it is already Set or Vary. Random table shapes (when "change table shape" is on) follow adjustable size limits shown on the Random tab: circles and octagons are as wide as high, 800 to 1200 mm by default (the user can set the minimum lower, for example 600 mm for mini tables); rectangles and stadiums are 600 to 1200 mm high and their width is the height times a factor picked evenly between 4/3 and 2 (sizes in steps of 50 mm; a min above the max is swapped when a round runs). Small tables (down to 600 mm) are intended mini tables: the randomizer changes nothing else to suit them (not the player-area line, the origin, the hand or the players). A dealer notch is made at most 70 % of the straight part of its side and left out when that is shorter than 150 mm. Shipped defaults (chosen by the maintainer): change table shape on, words off; Set on for the player-area line (shown), the dealer notch (off), the poker hand, pot, burn cards and muck (shown), Show players (shown) and Dealer is a player (on); Vary on for the number of players, Set on for cards per player (2); interval 5 s.
- **Casino name of the project and name styles (V67):** the project has its own field `casinoName` (artwork part, field at the top of the Artwork tab, default "Molino Royale"), independent of the text objects. Texts have the flag `nameWord` ("Part of the casino name" in the text panel; the two default big texts and the name words of Create casino have it, helper and new texts do not; a copy made with Clone or Add text never has it). A file without `casinoName` and flags gets them from its big texts (size at least 60 % of the biggest), the name being their texts joined. The randomizer row **Name style** (Vary, Set, value; shipped default Set "As written"; with neither ticked the texts are left as written) has three styles. *As written*: the user's texts as before. *Split*: the name is cut into 1 to n pieces of neighbouring RAW words ("of" and articles can be pieces of their own; 1 piece means no split), each piece a text of its own, fonts the same or different (random), laid out by the normal layout (row, stack or scatter, reading order rule holds). *Monogram*: the initials of the `nameWords` units as big separate texts side by side (initial = first letter of each unit; "of" never gets a letter; a leading article of the first unit is shown or hidden at random: "The Club of Royal Flush" gives T R F or C R F, "Le Diable" gives L or D; the maintainer's example "LD" is not produced because the unit rule joins the article to its word), fonts the same or different, and the full name small, as wide as the initials row, above, below or (a third of the rounds) over the initials, with an outline that knocks a hole in them and always the top text. A style hides the user's name texts (flag `styleHidden`, only those that were visible) and inserts its own texts (`gen`: `split` or `mono`, colour and outline copied from the first name text, colours never changed) where the first name text was; the next round removes them first. Everything is one undo step per round; the made texts, the hidden flags and the name are saved in the project; measurements attached to a made text become broken when the round replaces it. **Back to my own texts** (Artwork tab top and Random tab) removes the made texts and shows the hidden ones (one undo step). The other texts (not part of the name) keep their words in every style; the option "Also change the fonts of the other texts" (shipped on) decides whether their font, weight and letter space change; their place always does. With "change the words" the new name is written into `casinoName`, the name words get `nameWord`, and the style is applied on top. Open questions are in PROGRESS.md.
- **Casino name inventor** (since V52 the word lists named here, such as `HANDS`, `BLOCK`, `SINS`, `CONTAINERS`, `OWNER_PL`, `PLURAL_OK`, are lists in `data/words-basic.json`; the patterns stay in `js/random.js`; see Word lists): name patterns are adjective + noun, name + suffix, adjective + place, French article names, place + noun, possessive (`Devil's Gambit`), rank or title "of" suit or place (`Seven of Spades`; the two is called Two or Deuce half of the time each), hand names (`HANDS`, used alone or with a suffix) and themed names (`Black Devil`). Possessives and themed words are grouped (dark, holy, card, table, beast); a group only takes head words or adjectives that sound right with it, and `BLOCK` lists pairs that came out silly. Add new words to the group whose theme fits. The no-repeated-word rule ignores apostrophes and "of". The apostrophe is the straight one. Countable nouns can be plural (`PLURAL_OK`, plural by rule); owners in `OWNER_PL` can take a plural possessive (`Devils' Den`, apostrophe only). Hand names are whole phrases in `HANDS` (Royal Flush, Full House...); a suffix that repeats a word of the phrase is never used. "Pair of" / "Set of" + a plural rank is a pattern. The seven deadly sins and Wealth are in `SINS` (noun and adjective pair each): sins are owners (`Greed's Den`), take suffixes, and their adjectives go with people (`Greedy Dragon`). Longer names (three to five words): container + "of" + object (`Club of Royal Flush`, `House of Kings`, `Den of Sinners`, `Temple of Greed`) and `The Devil's Saints`; "The" may start a name and glues to the next word. Add new containers to `CONTAINERS`. The name is split into big texts by `nameWords`: "of" joins the word before it, articles (a, the, Le, La, Les) the word after. **Reading order of the name on the cloth:** the first word is never lower than the next, and at about the same height it is to the left (words may be above and either side of the next word). The scatter layout keeps the order too. With "change the words" off the order is the order of the text list.
- **Word lists (universal and project):** all words of the casino-name inventor are data, not code. The shipped basic words are `data/words-basic.json` (format `poker-table-designer-words`, version 1; lists such as `fullNames`, `helpers`, `adjectives`, `nouns`, `places`, `names`, `suffixes`, `pluralNouns`, `ranks`, `phrases`, `containers`..., maps `owners`, `heads`, `articled`, entry lists `themed` and `ofTitles`, and `block` for silly pairs). Add new words to the JSON, run `python3 scripts/make-words-js.py` and commit both files (the page cannot fetch JSON from `file://`, so the generated `js/words-basic.js` is what the page loads). At run time the bank is the unique union (case-insensitive, max 5000 words per list, 80 characters per word) of the **universal words** (the shipped list, or the user's own list that replaces it, kept in the settings; Reset on the Random tab goes back to the shipped list; an empty replacement is refused) and the **project words** (kept in the project). The project has a switch `useUniversal` (default on). A pattern only runs when all lists it needs are non-empty, so a project with the switch off and only `fullNames: ["Vanha Paja"]` always makes exactly that name. There are no inflection rules: the user writes every form he wants (plural, possessive, Finnish cases) as its own word, in the lists that already exist (plural nouns, owners...). Words can be edited as JSON (JSON window parts `words` and `universal`, with Copy, Paste, Apply, OK and Cancel), saved to and opened from files (Random tab). **Importing JSON:** any JSON can be pasted or opened anywhere; the receiving place interprets it, and the kind is found from the keys (`tables`, `artwork`... project; word list names: words; `units`, `snap`...: settings); the `format` key is only a help. There is no difference between a universal and a project words file (same format); the place decides. In the project words window (and Open project words) the words replace the project's words without a question. In the universal window (and Open universal words) a dialog asks: replace the universal list, add to the universal list, or copy into every open project (adds the words to each open project's own list; these are separate copies, later changes to the universal list do not reach them; one undo step per project). A words text pasted in the general paste place or opened with Open also offers "This project only (replaces its words)". A project or settings text pasted in a words window is loaded as what it is. Word packs, editable name templates and a seed for the inventor are only suggestions (see PROGRESS.md), not decided.
- **Settings file versus project file:** the settings (config) hold what is shared by all projects: units, snapping, the list of cutters (`cutters`, each with its calibration) and the heat press size (`pressMm`, default 380), favourite fonts and the user's universal words. The project holds everything else of one design: tables, guides, constraints, artwork, cloth, palette (moved from the settings; an old settings palette is ignored), fonts used, export choices, the words (`words`: project lists plus `useUniversal`), the randomizer options (`randomizer`), the view switches (`view`: centre mark, grid, origin, dealer line, names, extremes, dim outside, preview style) and the name of the cutter it uses (`export.cutter`; empty means the first one) and a copy of that cutter (`cutter`; when a project is opened and no cutter of that name is in the settings, the copy is added to the list; otherwise the settings keep their own). Older settings with a single `cutter` and `calib` become a one-cutter list. View switches, randomizer options and the cutter copy are saved with the project but are not undo steps (the undo snapshots leave them out and Undo never changes them). A project file without these keys loads with the shipped defaults when it is opened as a project or in a new tab; merging a partial file keeps the current ones.
- **Project tabs:** every project is a tab above the canvas (below the toolbar) with its own undo history and its own autosave key (`poker-table-designer-tab-<id>`; the tab list and active tab are in `poker-table-designer-tabs-v1`; the single project of older versions becomes the first tab). Tab buttons: New project (empty default project; the toolbar New button and the Project tab's New project do the same: a new project ALWAYS opens in a new tab and never replaces the current one), Duplicate tab (copy placed next to the original), Open in new tab (file picker), move left or right (tabs can also be dragged), × to close (an untouched tab, with no changes and no undo history, closes without a question; any other tab asks "Are you sure you want to close ...?"; closing the last tab leaves a fresh empty project). The ordinary Open loads into the current tab (merging as before). Switching tabs stops the randomizer. Units and the other settings are shared by all tabs. The tab name is the project name.
- **Demo mode (PLANNED, NOT BUILT; agreed with the maintainer, implement only when he says so):** a page address option (for example `?demo=...`) makes the page a presentation: it fills the whole window (browser full screen where allowed), shows no panels, toolbar or tabs, only the stage, and runs the randomizer all the time. The project comes in the address as Base64 of a compressed project (so a link is a complete demo; sizes of addresses need checking). A button on the Export tab makes the link of the current project. The randomizer options come from the project (as saved with it). Below the stop button of the randomizer there is a countdown or progress bar to the next change (the Random tab already has one; the demo needs the same in a minimal form). Open details to settle before building: how to leave the demo, address length limits, whether fonts that are imported from files can be carried (they cannot, only Google Fonts by name), and what the Artifact host allows for full screen.
- **Measurements (phase 1 BUILT in V54; phases 2 to 4 still PLANNED, see PROGRESS.md, Planned):** lasting, visible distances between things (CAD: dimensions), in the "Guides and measurements" tab (the former Guides tab), saved in the project (`measures`, part of the undo snapshots), never cut, attached to objects so that they follow them. Texts carry a permanent `uid` (assigned on save, unique, kept when other texts are deleted; `l1`, `l2` are still renumbered). Kinds: point to point (aligned, horizontal, vertical), ray (start point, direction towards a table centre or along an axis, target line, first crossing), shortest distance between two line elements, distance along a guide between two crossings. Anchors are named objects, never coordinates: table centre, node, edge or arc middle, card-line end, line centre, inner or outer edge of a thick line (card lines and the player-area line; the edge of the curved player-area line is the centre point moved half the thickness along the normal, outer = the side nearer the table outline), text extreme or centre, crossing of two lines, nearest point along a line, cloth centre, artwork origin; a free point (Alt or Ctrl) is the only coordinate anchor. Not attachable: chips, cards, the dealer button, players. While placing, a ghost (dashed) shows the measurement that a click would add, with its value, and the snap kind is named at the pointer. Dragging the number moves the dimension line sideways (`off`). A clicked measurement is selected (end point handles appear): drag an end point to attach it to another snap point, choose line centre or inner or outer edge for an end on a card line in the panel, press Delete to remove it; clicking elsewhere deselects. Look (decided by the maintainer): bright green (`#3dff7a`, not used by anything else), one pixel lines that do not scale with the zoom, arrow heads of a fixed screen size (5 mm at 96 dpi, smaller only on very short lines) so that they are always visible. Measurements are drawn above the click targets of the artwork so that they can be grabbed. The end of a ray on its target line and the ends of a shortest-distance measurement are not anchors but results; for a thick target line (card lines, player-area line) the measurement has `tref` (ray) or `r1` and `r2` (shortest distance), each `centre`, `in` or `out`, chosen by dragging that end or in the panel (the edge is the line offset half the thickness per segment). End point handles are drawn above the transparent grab line of the dimension. A measurement with a missing object stays in the list marked broken. A toolbar switch (`showMeasures`, a view switch saved with the project) hides them. Text outlines come from a hidden canvas trace (marching squares, simplified) with the setting `traceRes` (pixels per mm, default 10, in the settings file, shared by all projects); frozen texts use their exact vectors; when the font is not loaded the text box measured by the stage is used. The temporary Measure tool (toolbar) snaps to the same named anchors; a Pin button in the toolbar (or Enter) turns a finished temporary measurement into a lasting point-to-point measurement attached to those anchors (V64). Tab cycles through the snap candidates at the pointer while placing or measuring (the index resets when the pointer moves). Snaps added in V64: quadrant points of arcs of table outlines (anchor `tquad`) and the perpendicular foot onto a line from the first point (anchor `perp`, which resolves to the nearest point of the line to the first anchor). Tangent snap (V65): the point of an arc of a table outline where a line from the first point touches it (anchor `tang`, two solutions per arc). Not yet: arcs of text are polylines, layout sheet and picture do not show measurements.
- **Fonts:** import from TTF or OTF files. A source URL is stored only as informational metadata. Fallback chain: embedded in project, Google Fonts by name, browser memory. If a font is missing, warn, show a fallback font and offer "Load font file". Text can be live, embedded or frozen to geometry (outlines via opentype.js); unfreezing keeps the original spec.
- **Tables:** N top-down table outlines over one shared cloth artwork, each with name, size, end style or radius, colour, visibility, placement and wrap allowance. An outline is a closed node list of lines and arcs (a node has x, y and a bulge, where bulge is tan(angle/4) of the segment that starts at that node; 0 is a line, 1 a half circle). Presets (stadium, rectangle, octagon, circle, with an optional dealer notch as scoop or box) generate nodes; moving a node makes the outline free. Each table also has a rail ring and a player-area ("bet") line, an inward offset of the outline with an optional gap. The cloth is infinite by default; a toggle shows a real cloth size. The origin is the cloth centre mark.
- **Lines above texts, outlines on by default:** the player-area line is drawn and cut above all texts, with an outline (margin) that knocks a hole in whatever lies below it. The lines-and-cards band is above all texts by default and has an outline. New texts have an outline by default; the two big default texts (Molino, Royale) do not. If the randomizer has "change table shape" on and there is no table, it creates one. Clicking a text on any tab brings the Artwork tab forward. The randomizer never changes outlines or colours, but may show or hide the player-area line. View switches (centre mark, dealer line, player-area line) are in the toolbar and work while the randomizer runs. The dealer line marks the mouth of the dealer notch on the stage only and is not exported.
- **Table decorations:** pot (chips), burn cards and muck (folded cards) next to the hand, set with offsets and sizes in the Lines & cards panel. The hand, burn cards, muck and pot are table objects, not cloth pattern: they are always drawn above all texts, lines and the player-area line whatever the layer order (bottom to top: muck, burn cards, hand, pot chips, players); the layer order of the lines (`band.at`) only places the two lines. Clicking the hand still selects Lines & cards. The hand is in the picture and the Blender texture, the other things only in the picture; none is cut. Each table has a switch for its dashed wrap line (also a toolbar switch for all visible tables); the randomizer never changes it. The Random tab can show, hide or vary the pot, burn cards and muck.
- **Things on the table:** pot, burn cards, muck and players (1 to 12 per table, 2 to 4 cards each, one to three chip stacks, dealer button, random Hold'em snapshot) come from one seeded generator in `scene.js`. They show on the stage and in the picture (option), are real 3D objects in Blender (chips 40 mm x 2 mm by default, button 70 x 4 mm, 0.1 mm air gaps), are not in the Blender texture and are never cut. The randomizer only changes them through the Vary and Set rows of the Random tab. Card size modes: Poker 64 x 89 mm and Custom; the gap between the lines never changes the card size (the hand stays centred and may overlap the lines). The automatic randomizer keeps the casino name and texts unless its words box is ticked. Pot, burn and muck offsets are measured from the centre of the gap between the two lines.
- **Number fields:** dragging sideways over a number field or its label scrubs the value; a click still edits. Burn cards are always below the pot (drawn first, chips over them rest on top). Resizing a table (fields, scrubbing, or dragging a circle node) keeps its centre in place so the artwork stays put relative to it; a circle stays a circle. Default offsets: pot -270/-50, burn -250/30, muck -450/10; pot, burn cards and muck are shown by default.
- **Lines are centre lines (V59):** every line is its mathematical centre line and the thickness is spread evenly on both sides. For the two card lines `band.gap` is the distance between their centre lines (the lines are drawn at `y - gap/2` and `y + gap/2`, each `thick` wide around that), so a 100 mm gap measures 100 mm whatever the thickness. The player-area line was already a centre line; table outlines and guides have no thickness. Measurements attach to the centre line by default (`line centre`); the `inner edge` and `outer edge` of a thick line are separate named anchors the user can choose by pointing. No migration of older files was wanted by the maintainer (there are no files to keep). Planned, not decided: aiming a real adhesive line at a guide on the cloth by its centre.
- **Settings tab (V64):** a separate Settings tab (not the Project tab) holds what is not part of any project: the settings file buttons (Save, Open, Reset settings, Settings JSON) only; the cutter and the calibration moved to the Cutters tab (V69, see below). The Project tab keeps the paste box, the project buttons and the project text. Decided by the maintainer.
- **Tooltips, help and examples (V65):** every button, choice and switch has a tooltip (`title`). `js/help.js` fills the missing ones after every panel render from tables keyed by `data-act`, `data-k`, id, tab, tool or save kind, and falls back to the aria-label or the text; a test fails when anything has none, so every new button needs a line in `TIPS` there. F1 or the toolbar Help button opens the help window at the topic of the current tab or tool (topics are data in `help.js`: getting started, artwork, tables, guides, measurements, Measure tool and Pin, colours, fonts, randomizer, export, projects, settings, keyboard); Esc closes it. Examples ("Generate example" in the measurement panel, "Show me" buttons in the help) play a real action slowly: a visible pointer moves over the stage, the real tool is chosen, and real pointer events are sent, so the example goes through the same code as the user (point to point, horizontal, vertical, ray both kinds, shortest distance, along a guide, temporary Measure plus Pin, placing a guide). The result is a real change with one undo step; any key or click stops an example and leaves nothing behind. Examples are made from what is in view; when nothing fits, a line says what to do (for example place a guide first). Help texts are English like everything else in the repository. Ideas for more examples are in PROGRESS.md, Planned.
- **EPS for Roland CutStudio (V66):** CutStudio cannot import SVG; its EPS reader understands only `x y m`, `x y l` and `x1 y1 x2 y2 x3 y3 c`, wants closed paths closed by repeating the first point with `l` (never `h`), and needs one extra `0 0 m` at the end. `js/eps.js` writes that: a fixed template (own text, same structure as the Inkscape plugin `inkscape-roland-cutstudio`, bounding box -10000..10000, prolog with the short operators, `q q`, 0.5 mm line width, one stroked path, `0 0 m`, `S Q`, `Q Q`, `showpage`, trailer), lines only (no fills, groups, clipping, text), arcs as cubic Beziers (at most 90 degrees per curve, a circle is 4 curves, radius error below 0.03 %), 3 decimals. Input is millimetres with y down; output is points (1 pt = 25.4/72 mm) with y up and the drawing's lower left corner at 0 0, so it is not upside down. A `post` matrix is applied last: that is where a later mirror goes (not built). Crop marks (`%%RolandCropMark`) are not built. Warnings (empty drawing, one-point paths skipped, drawing outside +-10000 pt) are returned, never silent. **Licence decision:** the plugin is GPL-2.0-or-later and this project is MIT, so nothing of the plugin's code or template text is copied; the template is written from scratch and the plugin is credited in the file header as the source of the format knowledge. The maintainer verified in a real CutStudio that this independent template opens, so the GPL fallback is not needed. Where it is used: the calibration zip contains `calibration-horizontal.eps` and `calibration-vertical.eps` next to the other files (maintainer's request). The cut export also writes it (V69, see Cutters and the cut export). Test files for a real CutStudio are in `tests/cutstudio/` with instructions.
- **Cutters and calibration (V69, decided with the maintainer):** a main-level **Cutters** tab (after Export). The list of cutters lives in the settings (`config.cutters`; add, duplicate, delete with a two-click confirmation, reorder, select; JSON window part `cutters`; Save/Open cutters file). A cutter: `name`, `widthMm` (cutting width across the roll, default 500), `maxLengthMm` (0 = no limit), `thinMm` (thinnest detail that cuts and weeds well, default 1, adjustable) and `calib`. The project uses one cutter by name (`export.cutter`, "" = the first) and carries a copy; the heat press area is a global setting `pressMm` (default 380). **Calibration:** shared strip count (default 3, 2 to 6), lengths adjustable per direction (defaults 100, 250, 480; X at most the cutting width, Y at most the longest cut or 2000, at least 60 mm); the strips are stacked (horizontal) or side by side (vertical) in one file with a 20 mm gap, in table order; the zip still has 14 files. Per direction a method: *simple* (the overall length of one chosen strip; blade offset taken as 0, honest about that) or *detailed* (four measurements per strip: 1 overall length, 2 block span from the first block's left edge to the last block's left edge, 3 block width, 4 gap width). The maths (`js/calfit.js`): every number is one equation `measured = a * nominal + c * 2d` with the scale a of the cutter and the blade offset d per edge (overall and block width: c = +1, gap width: c = -1, span: c = 0), least squares; the correction factor is 1 / a; if the numbers cannot separate a and d, d = 0. The results table shows the error of each number in mm and percent and the residual; warnings for a scale more than 10 % off, an offset above 1 mm, residuals above 0.3 mm. The correction is shown and editable as factor, percent and millimetres over the longest strip (typing one overrides the measurement until "Use the measurements"); the blade offset is the mean of both directions (a warning when they differ) and editable. No measurements means factor 1 and offset 0. A guided measuring window (schematic strip with numbered red arrows, instructions, the same entry tables) and a measuring-guide PDF (A4, marked "not to scale, not for cutting", instructions and blank tables, written by `js/pdf.js`) help to measure the kept (positive) piece with a caliper at mid-edge, not at corners. Not built: automatic reading of measurements from a photo.
- **Cut export since V69:** format SVG (one file, layers) or EPS (one file per colour in a zip, or a single file for one colour; all colour files share one frame, so the colours register). Order of the geometry: the user's scale (design axes, before rotation), mirror and rotation, the calibration correction of the cutter times the extra manual factors (cutter axes, after rotation), the booleans (upper objects hide lower ones), then the blade offset: outer rings inward and holes outward by the kerf (a positive value means the kept pieces come out bigger), then the clip to a table and the split into strips. The offset is approximate (mitre joins with a limit; near thin parts it can leave small artefacts) and is skipped with a warning when Paper.js is not loaded. Check boxes: use the calibration correction, apply the blade offset (both default on). **Filters:** texts, upper card line, lower card line, the player-area line (the old "include" box), only the selected elements (texts and the card lines), keep the position (the frame is the whole design including what is filtered out; default off, the frame is the output). Filtered-out items still knock holes in what is below them (the player-area line follows its own box and is left out entirely when unchecked). **Jobs** (`export.jobs`: name, filters, selected ids, done) save a set of filters; Use, Export and Done actions. **Scale** (project-level `export.scaleX`, `scaleY`, `scaleLock` default on): editable as factor, percent and millimetres (width and height of the output at that scale, from the size of the whole export set of all colours), Fit to roll width (across the roll after rotation), Fit to the heat press (uniform), Back to 100 %. The halo width scales with the mean scale. It applies to the cut files only, not to the PNG picture, layout sheet, Blender or measurements, and shows in the file name (`-50pct`, or `-x50pct-y80pct`). Warnings: output wider than the cutting width or longer than the longest cut, lines or outline gaps thinner than the cutter's thinnest detail after scaling (exact), text smaller than eight times the thinnest detail (a rough guess, said so in the message).
- **Calibration images (V63; since V69 per cutter in the Cutters tab, with several strips per file, see below):** the Download button makes one zip (`calibration-images.zip`, store only, built in the page) with 14 files: for the horizontal strip (across the roll) and the vertical strip (the same pattern turned 90 degrees clockwise) two SVG files (`-filled.svg` solid black, `-outline.svg` a hairline path, stroke 0.01 mm, no fill; both in millimetres, tight to the shape), one EPS file for Roland CutStudio (`calibration-horizontal.eps`, `calibration-vertical.eps`, lines only, see EPS for Roland CutStudio) and PNG and JPG at 300 and 254 dpi (`-300dpi`, `-254dpi` in the names; 254 dpi is exactly 10 pixels per mm). Bitmaps have a white margin (default 5 mm), every pixel exactly black or white (thresholded, so JPG at quality 95 is the only lossy one), and the dpi is written into the file (PNG pHYs, JPEG JFIF). The strip (shape A, chosen by the maintainer): a 10 mm bar across the roll, default longest length 480 mm (the roll is 500 mm wide; V69 has several lengths per cutter), 10 x 10 mm blocks starting at every even centimetre (0, 20, 40 ...), and at 0, 100, 200 ... a 15 x 5 mm foot whose left edge is the block's left edge and which reaches 5 mm into the gap to its right (the foot also shows which end is the left one). It is one closed contour. Not part of the project and not part of the cut export. Mirror and rotation handling of the calibration cut is not built.
- **Lines and cards fields:** length, gap, thickness and outline width are always in millimetres whatever the unit setting is (labelled), thickness in steps of 0.1 mm.
- **Player-area line defaults:** 200 mm from the edge, 3 mm thick (existing projects keep their values).
- **Lines defaults:** the card lines are 380 mm long, 100 mm apart (gap), 4 mm thick, with the outline on and 3 mm wide; the card size is Poker (existing projects keep their values). Opening or closing a text panel keeps its header at the same screen position; the panels below move.
- **Convert buttons:** the Shape heading of a preset table has exact conversion buttons at its right. Stadium to Rectangle (always; corner radius = half the shorter side, so the outline is identical), Rectangle to Stadium (only when the corner radius equals half the shorter side within 0.5 mm; otherwise the button is greyed out and a visible line says to increase the radius to that value), Stadium to Circle (only when width equals height within 0.5 mm and the dealer notch is off; otherwise greyed out with the reason), Circle to Stadium (always, same width and height, a locked circle gives a circle-shaped stadium). Each is one undo step and the notch, position, rail and player settings are kept. Octagons and free outlines have no convert buttons. The old preset menu still changes the type roughly (size from the bounding box, default radius).
- **Circle and oval:** a circle preset is round and has a lock for its aspect ratio (on by default): locked it shows Diameter and Radius, unlocked it shows Width (X diameter) and Height (Y diameter) and becomes an oval made of four arcs. Corner radius and chamfer can never go below 0 (chamfer below 1 mm is raised to 1).
- **Artwork origin:** texts, the lines and the hand (and so the pot, burn cards and muck, which are offsets from the hand) are stored measured from the artwork origin; edge elements (tables, rail, player-area line, players, guides) stay measured from the cloth centre, which is the one fixed origin. The artwork origin is a free point on the cloth: `x` and `y` in mm from the cloth centre, default (0, 0), and it never moves by itself (not when a table is resized, turned, hidden or replaced). A quick button computes the point once; its text shows the distance ("Place at 300 mm from dealer edge") and the number field right next to it sets that distance (default 300 mm, the arm length; the table is chosen below it, first visible table by default), and a read-only line under it tells where the origin is now (mm in from the dealer edge and mm sideways, measured from that table) and writes it into x and y; with a dealer notch the distance is measured from the bottom of the notch, and the point is at the centre of the dealer side. The dealer position is the first crossing of the outline from the middle of the table towards the dealer side (the notch side when the notch is on, otherwise the bottom). Moving the origin moves all artwork with it. The artwork stays upright whatever the table rotation. The origin is saved in the artwork part (`artwork.origin`: x, y, distance, table); files without it (older projects, logo-editor files) get (0, 0), so they look exactly as before; a short-lived V33 origin with `mode` is converted once into the fixed point it showed. Default artwork: hand 82 mm below the origin, big texts 65 mm above it. A pink diamond marks the origin (toolbar switch). Cut file, picture, Blender texture and objects, layout sheet and the randomizer all convert to or from this origin.
- **Design aids are not cut:** the poker hand, pot, burn cards, muck and players only help the design stage and are never part of the cut file.
- **Real-world facts (given by the maintainer, 2026-11-04):** the heat press is a **Stahls' The Maxx Press** with a pressing area of **380 mm x 380 mm** (this replaces the earlier 390 x 390 mm guess) (product page: https://stahlseurope.com/heat-presses/maxx-series/). The material that is cut is not plain vinyl but **polyurethane film** ("Stahls' CAD-CUT Sportsfilm P1", a heat-transfer film), on a roll **500 mm wide and 25 m long** (roll product page: http://www.lamtekno.fi/c507-stahls-cad-cut-sportsfilm-p1-fi.html). The press area and the roll width are meant to be used later as optional limits or, at least, as guide lines on the canvas to aim with (see Planned in PROGRESS.md). Since V69 the roll width is the cutting width of a cutter (default 500 mm) and the press area is the setting `pressMm` (default 380); the Export tab has Fit to roll width and Fit to the heat press buttons. Guide lines on the canvas are still not built.
- **Production pipeline (agreed, not built yet):** vectorise (halos become holes), then split into pieces along a grid (heat press 380 x 380 mm by default (see Real-world facts), adjustable, grid from the artwork origin), then name each piece and vectorise the name as a small cut label next to the piece, then cut everything. Splits overlap neighbours by an adjustable amount, made after the boolean subtraction. Long narrow pieces are turned across the roll to save roll length. Roll width and press grid are shown as optional guides on the canvas. The table that is highest in the table list is the topmost one and the only one that shows players when several tables are visible. Calibration can be exported as a full square, horizontal only or vertical only. See PROGRESS.md, Planned.
- **Table summary:** a line per visible table under the status bar (cursor, zoom, mm per 100 px): name, type, diameter for a round table, otherwise width and height, plus the roundings (stadium end radius, rectangle corner radius, octagon chamfer). No other values.
- **Layout sheet:** a readable, downloadable marking guide (centre cross, outline key points, guide lines measured from the centre or the outline, check diagonals). Always measure from the centre, never chain.
- **Palette:** named, editable colours (defaults felt green `#0d2b22`, gold `#d4af5a`), one cut layer per colour, flat or shaded preview.
- **Cut export:** boolean union and subtract (Paper.js, loaded from a CDN at runtime; without it shapes are exported overlapping), upper halos hide lower objects, closed non-crossing contours, tolerance 0.01 to 0.05 mm, mirror, rotate 90/180/270, separate X and Y correction factors, calibration, cutter profiles, strips split to cutter width.
- **Constraints:** dimensions as reference or driving constraints, a linear solver for axis-aligned guides (fixed, distance, minimum, maximum, equal spacing, symmetry, ratio), conflict reporting that names the constraints involved.
- **Blender export:** a Python script generated from the project (table outline and rail, cloth texture rendered from the artwork, room sized to the table). The template lives in `blender/src/scene_template.py`.

## Decisions that were considered and rejected (and why)

- **An artwork origin that follows the dealer edge of the table (first version).** Rejected: the artwork moved by itself whenever a table was resized, turned, hidden or replaced, which contradicted "the centre and the artwork stay put" and needed Auto, anchor-table and fallback rules. Replaced by a fixed free point with a button that places it once.
- **Card size that fits the gap between the lines.** Rejected: changing the gap must never change the card size; sizes are Poker or Custom.
- **Players on every table when several tables are visible.** Clutters the cloth; planned: only the topmost table in the list shows them.
- **Converting a stadium with a dealer notch to a circle.** Blocked with a visible reason instead of silently dropping the notch.
- **Greyed-out buttons without a reason.** Every disabled convert button says why and what to change.
- **Cutting the poker hand, pot, burn cards, muck or players.** They are design aids only; they are never cut.
- **Halos approximated at seams.** Splits and overlaps are made after the boolean subtraction so that they only copy visible geometry.
- **Drag-only handling of the artwork origin.** Origin is set by numbers and the button, because dragging would just move all artwork at once.

# Contradiction First

Be a critical, analytical partner — not a mere executor.

When I ask you to do something:

1. **Evaluate the request first.** Before you start, check for contradictions, ambiguity, hidden assumptions, or goals that fight each other.
2. **Flag it immediately.** If you find a problem, say so directly and concretely — do not soften or skip it. State what conflicts with what, and why it hurts the outcome.
3. **Propose a fix.** Offer a short, clear alternative or a clarifying question that makes the request consistent. Do not wait for permission to point it out.
4. **Execute only after that.** Once the request is clear, or I have confirmed the contradiction as a deliberate choice, do the work carefully.
5. **Do not be a people-pleaser.** Do not praise a weak idea, and do not hide problems behind politeness. Be direct, precise, and useful.

If the request is already clear and consistent, say so briefly and go straight to the work — do not invent problems.
# Language rule

**Everything that goes into the project and its repository must be in English ( with a few exceptions )**, whatever language the conversation with the maintainer is in.

## Default / What must be in English
All content Claude writes to the repository MUST be in English. This covers:
source code, identifiers, code comments, documentation, README files,
commit messages, branch names, PR/MR descriptions, test names, config comments,
and generated reports.

- Source code: identifiers (variables, functions, classes, files, folders), string constants, log messages, error messages and exceptions
- Code comments: inline and block comments, docstrings, JSDoc/KDoc/Javadoc, TODO/FIXME notes
- User-facing text: UI texts, labels, buttons, menus, placeholders, tooltips, notifications, validation messages, empty and error states, in-game text
- Documentation: README, CONTRIBUTING, CHANGELOG, architecture and design documents, ADRs, API docs, setup guides, rule notes
- Configuration and metadata: config file comments, package descriptions, environment variable descriptions
- Tests: test names, descriptions, assertion messages and test data labels
- Data files: data labels, seed data, table and column names, migration descriptions
- Version control: commit messages, branch names, pull request titles and descriptions

## Conversation
- Reply to the maintainer in the language they write in (for example Finnish). This applies to explanations, questions and status updates in the chat.
- Write every project artifact in English, regardless of the chat language.


## Localization

- Do not write Finnish (or any other language) into the UI or code unless the maintainer explicitly asks for localization or i18n support.

## Preserve user-provided material
- Never translate, rewrite, or "normalize" content the user supplied
  (documents, specs, data files, quoted text, existing files). It keeps its
  original language.

  existing language. Do not convert the file to English.
- When quoting user material inside an English document, keep the quote
  verbatim in the original language and add an English summary if needed.
